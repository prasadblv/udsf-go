# Development

## Requirements

- Go (see `go.mod` for the version)
- Docker, for the integration tests and the Compose stack
- `openssl`, for `generate-cert.sh`
- Optional: [air](https://github.com/air-verse/air) for live reload, [k6](https://k6.io) for load tests

## Build, run, test

```bash
./generate-cert.sh     # once; creates certs/server.pem and certs/server.key
make build             # produces ./udsf
make run               # go run cmd/api/main.go
make test              # go test ./... -v
make itest             # Redis integration tests (internal/database), via Testcontainers
make watch             # live reload with air
```

`make test` includes `internal/database`, whose tests start a Redis container, so Docker must be running.

## Project layout

```
cmd/api/main.go                    Entry point, flag parsing, graceful shutdown
internal/config/                   Config structs, defaults, client TLS builder
internal/database/                 database.Service (Redis)
internal/observability/            trace.go, metrics.go
internal/server/                   server.go, routes.go, redis_ready.go
internal/udsf/api/                 *_crud.go / *_service.go per API group
internal/udsf/model/               Request and response models
internal/udsf/route/routers.go     Router assembly
internal/udsf/util/                Keys, block encoding, logging, helpers
openapi/openapi.yaml               API definition
```

## Generated code

Controllers (`api_*.go`), models, the router and parts of `util` come from OpenAPI Generator. The header
`Code generated by OpenAPI Generator ... DO NOT EDIT.` marks them. Files listed in
`internal/udsf/.openapi-generator-ignore` are hand-maintained and survive regeneration, notably
`api/api_block_crud_service.go`, `api/api_record_crud.go`, `api/api_record_crud_service.go`, `api/imports.go` and `util/helpers.go`.

The service files (`api_*_service.go`) hold the business logic. To implement an endpoint, replace the
`StatusNotImplemented` response in the corresponding service method, using `database.Service` for storage.

## Adding an endpoint implementation

1. Add the logic to the service method in `internal/udsf/api/api_<group>_service.go`, and give the service a `database.Service` as `BlockCRUDAPIService` and `RecordCRUDAPIService` do. If you add the file to `internal/udsf/.openapi-generator-ignore`, regeneration will not overwrite it.
2. Pass the database to the service constructor in `RegisterRoutes` (`internal/server/routes.go`).
3. Add unit tests next to the service, using a fake `database.Service` (see `fakeDB` in `api_block_crud_service_test.go` and the failure-injecting `errDB` in `api_record_crud_service_test.go`). Anything that lists or deletes by record should use the block index (`util.CreateBlockIndexKey`) rather than `SCAN`.
4. For timers, also add a `/nudsf-timer/*path` route in Gin so requests reach the generated router.

Run the functional tests against a running instance:

```bash
./functional-tests/test-block-crud.sh                      # https://127.0.0.1:9443
./functional-tests/test-block-crud.sh https://host:9443
./functional-tests/test-record-crud.sh                     # same arguments
```

It needs `curl` with HTTP/2 support; `jq` is optional. They print `PASS`/`FAIL` per request, and `test-record-crud.sh` exits non-zero if anything failed.

### Demo scripts

`bash-test/` holds two scripts that demonstrate the APIs rather than assert on them. They call curl with
`--http2 -k -v`, so every step shows the TLS handshake (ALPN `h2`), the HTTP/2 request and response headers, the
status code, and the response body. Each step prints the status it expects.

```bash
./bash-test/demo-block-crud.sh [base_url]       # create, read, replace, get-previous, list, binary round trip, delete
./bash-test/demo-record-crud.sh [base_url]      # create with blocks, read, meta, modify, get-previous, 412/400 cases, delete
TRACE=1 ./bash-test/demo-record-crud.sh         # curl --trace-ascii: also dumps request and response bodies
```

Both use a unique record id per run and clean up after themselves. Use `TRACE=1` to see the multipart request body
that `-v` alone does not print.

## Load testing

```bash
k6 run k6/udsf-block.js                             # 1000 VUs for 120 s against Block CRUD
BASE_URL=https://host:9443/nudsf-dr/v1 k6 run k6/udsf-block.js

k6 run k6/udsf-record.js                            # 1000 VUs for 120 s against Record CRUD
VUS=50 DURATION=30s k6 run k6/udsf-record.js        # lighter run
```

`k6/udsf-block.js` writes and reads blocks per VU, checks that responses use HTTP/2, and deletes its data in `teardown`. Each VU does two requests per second (it sleeps 1 s), so 1000 VUs top out at about 2000 req/s regardless of how fast the server is; remove the `sleep` to find the server's own ceiling (about 8800 req/s on one laptop with k6 and Redis on the same machine). The Compose stack limits the service to one CPU (`UDSF_CPUS`, default `1.0`) and exports traces, metrics and logs, so its numbers are lower than a bare local run.
`k6/udsf-record.js` does the same for records. Each VU repeatedly `PUT`s its record (multipart `meta` plus one block),
`GET`s the record and its meta, and `DELETE`s the record every tenth iteration. It sets thresholds (checks above 99%,
under 1% failed requests, p95 under 500 ms, overall and per operation) and removes every record in `teardown`; the k6 summary lists each operation's latency separately. Options come from the environment:
`VUS`, `DURATION`, `BASE_URL`, `POOL` (block ids per record), `DELETE_EVERY` (0 disables in-test deletes) and `SLEEP`.
Make sure the target is the server you mean to test: the Compose stack also publishes port 9443, and a locally started
server cannot bind it while the stack is running. Use a different `server.https_port` and `BASE_URL` to compare builds.
Avoid `SCAN` on request paths; it visits every key and was the cause of multi-second p95 on `GET`/`DELETE` of a record
(see [architecture](architecture.md#storage-layout)).

`k6/hello.js` is a minimal smoke script. For profiling during a run, set `server.enable_pprof: true` (the shipped configs do), save a profile with
`curl -k -o cpu.prof "https://127.0.0.1:9443/debug/pprof/profile?seconds=30"` and open it with `go tool pprof cpu.prof`.

## Docker image

The `Dockerfile` uses a multi-stage build and produces a static binary in a distroless, non-root image. The
certificate and configuration are mounted at runtime; the default command is `-config /config/udsf_config.yaml`.

```bash
docker build -t udsf:latest .
docker run --rm -p 9443:9443 -v $PWD/certs:/certs:ro -v $PWD/config:/config:ro \
  udsf:latest -config /config/udsf_config.docker.yaml
```

The container needs a reachable Redis; use Compose to start one alongside it.
